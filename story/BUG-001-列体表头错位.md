# BUG-001: 事件列与表头错位

**日期**: 2026-05-30  
**现象**: 主事件显示在错误的员工列下（朴美善的事件显示在陈茜列）  
**根因**: `buildDepartmentTree` 和 `headerLoader` 使用不同的排序键（UUID vs 中文名）  
**修复**: 1 行代码 — `buildDepartmentTree` 改按 `departmentName` 排序  
**耗时**: ~4 小时排查  

---

## 错误排查路径（反模式记录）

| 阶段 | 排查方向 | 耗时 | 结论 |
|------|----------|------|------|
| 1 | 怀疑匹配逻辑错误 | 1h | 在 mainEventLoader 中反复加诊断看 accountId 是否匹配 staffMap → 匹配完全正确 |
| 2 | 怀疑 events 数据错误 | 0.5h | 加诊断看 adapted events 的 resourceId → 正确，都是名字，和 resource.id 一致 |
| 3 | 怀疑 TimeCalendar staffEvents filter 错误 | 1h | 直接在 TimeCalendar 内加诊断 → 每列分配的事件完全正确 |
| 4 | 始终不相信数据正确 | 1h | 反复核对 accountId → 全部匹配 |
| 5 | 最终发现 | 0.5h | **表头（departmentTree）和列体（resources）排序不一致** |

### 为什么第一阶段就应发现？

**数据层面的所有匹配都是正确的**。第 4 次诊断（TIMELINE-COL）已经证明 TimeCalendar 内部匹配正确——朴美善列有"林妙好"事件，陈茜列只有"晚"。但还在怀疑匹配逻辑，因为没意识到**问题不在匹配，在视觉对齐**。

### 应该走的正确路径

```
怀疑匹配 → 一次诊断确认匹配正确 → 排除匹配 → 检查视觉 → 发现排序
                                    ↑
                              走到这里就该停了
```

---

## 根因

```
headerLoader.sort:  departmentName(pinyin)        → [技术巴, 客户巴]
buildDepartmentTree.sort: departmentId(UUID)        → [客户巴(9..), 技术巴(c..)]
                            ↑                           ↑
                        排序键不同 ← 是这个 bug
```

`resources` 数组（列体）按 `headerLoader` 的排序生成。`departmentTree`（表头）按 `buildDepartmentTree` 的排序生成。两者部门顺序不同，导致第 N 个表头标签对应的是第 M 个列体数据（N ≠ M）。

## 修复

```diff
- tree.sort(function(a, b) { return a.id.localeCompare(b.id); });
+ tree.sort(function(a, b) { return a.name.localeCompare(b.name, "zh"); });
```

`adapters.js` 1 行改动。`departmentId` → `departmentName`，与 `headerLoader` 排序键统一。

---

## 教训

1. **排序是隐式契约**：两个模块各自排序时，必须用同一个键和同一套规则，否则表单对不齐
2. **表头和列体必须同源排序**：如果两者分别排序，应从一个已排好序的源派生，而不是各自排
3. **"数据正确"不意味着"显示正确"**：第 4 次诊断已证实匹配无误，此时应立刻转查渲染/布局而非继续怀疑数据
4. **多看代码少加日志**：`buildDepartmentTree` 的 `tree.sort` 就在 adapters.js 第 64 行，一眼就能看到排序键是 `id` 不是 `name`
